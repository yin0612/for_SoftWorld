# 全站資料更新查核與改善規劃

查核日期：2026-10-01（台北時間）。範圍：GitHub Pages 的 for_SoftWorld 網站、八個分頁、Cloudflare Worker/D1、GitHub Actions 與公開資料快照。

## 查核結果

初次線上抽查共 1,802 篇，發現 5 筆未來時間；修正後第一次線上查核為 1,797 篇，未發現重複 URL 或未來日期。部分台灣 RSS 將本地時間標成 GMT，另有日期未帶時區，現已依來源正規化並拒絕未來時間。RSS 主收集有 6 個管道超過兩小時未成功，新增獨立每小時 RSS 備援後，本機實測 29 個啟用來源全部可讀、零收集錯誤。

「資料正確」在本次查核中指必填欄位、來源網域、日期區間、分頁完整性、去重、分類與統計口徑，以及可觀測的更新狀態。新聞報導本身的每個主張仍需人工查證；網站不得把來源驗證標記解讀為已完成逐則事實查核。公司簡介與產品主檔為人工維護，與自動新聞更新分開標示。

## 分頁與更新方式

| 分頁 | 資料與更新方式 | 本次處理 |
| --- | --- | --- |
| 產業總覽 | 公司主檔人工；近期新聞、文章數與實際來源數每 5 分鐘共用同步 | 移除固定近期事件；由最新公司相關文章產生卡片與彈窗；修正光聚更名年份及泰偉 Astro、橘子等誤歸類 |
| 關鍵字監測 | 完整近兩個月 API 資料每 5 分鐘同步 | 全分頁載入與游標檢查；URL 去重；依完整發布時間排序；保留篩選、日期與已展開的篇數 |
| 金融科技 | 由同一份資料套用金融科技規則 | 同步刷新清單、分類與來源統計；保留主題與文字篩選 |
| 遊戲產業 | 由同一份資料套用遊戲規則 | 同步刷新清單、分類與來源統計；保留主題與文字篩選 |
| 數據分析 | 同一份文章集合的實際數量、來源與分類、來源查核報告 | 分頁啟用時重繪圖表；資料更新時同步重繪；統一來源名稱；查核報告改讀原始檔與限時快取 |
| 對比工具 | 公司命中的實際文章、來源與分類 | 更新後重算目前已選公司；修正公司詞比對與已出售 IP 的錯誤歸因 |
| 趨勢分析 | 同一份文章集合的時間與關鍵字統計 | 更新後重繪趨勢與數字 |
| 資料說明 | 更新口徑、動態日期範圍與限制 | 日期範圍隨同步更新；明列排程、過期標準、人工資料與報導查核限制 |

所有動態頁面共用一個同步程序，避免各頁資料時間不同。每 5 分鐘同步；回到頁面、網路恢復及手動同步也會檢查。背景隱藏時停止不必要同步，回前景補查。同步失敗保留最後成功資料並顯示警示。

## 後端排程與失敗處理

| 管線 | 排程（台北時間） | 狀態與備援 |
| --- | --- | --- |
| Worker RSS 主收集 | 每小時第 17 分、12:00、17:00 | D1 保存文章、審核與執行紀錄；最後成功超過 2 小時視為逾期 |
| GitHub RSS 備援 | 每小時第 23 分 | 使用相同 RSS 解析、來源與規則引擎；按原文 URL 合併；全數失敗保留舊快照並使工作失敗；被拒絕的文章不得恢復 |
| Google News 聚合 | 每 6 小時，另於 12:00、17:00 | 部分失敗保留該來源既有資料並記錄錯誤；全數失敗保留上一版且使工作失敗；超過 8 小時顯示逾期 |
| 全站品質工作 | 每天 08:23、相關程式變更、手動觸發 | 檢查所有分頁資料、重複 URL、日期、必填欄位、完整篇數與新鮮度；異常使 Actions 失敗，保存 JSON artifact |

GitHub 排程可能排隊，無法保證準點。網頁每 5 分鐘同步是讀取上游最新結果，並不表示新聞來源每 5 分鐘產生新內容。Google News 為聚合結果，保留清楚的來源類型與原文跳轉，不宣稱為媒體官方 RSS。

## 已修正的重要問題

- 前端原本只在首次載入取資料，來源查核 Promise 永久快取；現改為共用自動同步與限時快取。
- 原本每日更新腳本為無效成功訊息；現改為實際檢查並產生可追溯報告。
- 原本只讀最多 2,000 篇且後端有隱藏上限；現讀完整分頁、按實際有效資料計算 total，發現中斷時提示不完整。
- 台北跨日與月底的近兩個月區間已統一；拒絕無法解析及未來時間。
- 「來源健康」改按最近成功時間判定；獨立 RSS 備援成功可證實來源仍可讀，主收集問題仍保留在後端紀錄。
- 計數動畫可能覆蓋新資料數字，現會在資料目標變動時停止舊動畫。
- 泰偉 Astro 不再命中 Astro 遊戲硬體；橘子不再只憑水果詞命中；大宇不再以已出售的仙劍／軒轅劍直接歸因公司。
- 公司近期事件改為實際文章連結；光聚更名時間修正為 2025 年 12 月，依[官方大事紀](https://group.softstar.com.tw/tw/history.php)。
- 機器人提交通常不觸發 Pages 重建，來源查核報告因此直接讀原始資料，依 [GitHub 官方說明](https://docs.github.com/en/actions/concepts/security/github_token)。

## 後續改善規劃

1. **優先：異常告警與維運紀錄。** 目前已可由 Actions 失敗與網站警示辨識問題；建議集中保存每次來源成功率、資料延遲與收集耗時，連續兩次異常再發送指定通知，避免噪音。通知管道需由管理者指定。
2. **優先：抽查內容與公司主檔。** 每週抽查公司／產業文章分類，保存人工覆核與誤報原因；每月核對董事長、公司名稱、產品與合作資訊，顯示查核人及最後核對日。來源網域合格並不保證新聞主張正確。
3. **下一階段：重構主收集任務。** 將 RSS 依來源拆成可重試小批次、限制 D1 查詢與並發，改善現在部分收集未完成的問題；依實際使用量評估 Cloudflare 方案，不直接假定需要付費。可參考 [D1 平台限制](https://developers.cloudflare.com/d1/platform/limits/)與 [Workers 平台限制](https://developers.cloudflare.com/workers/platform/limits/)。
4. **下一階段：降低重複計算。** 產生有版本號的完整資料快照與來源統一 ID；各頁沿用相同 snapshot version，避免分頁載入期間上游更新造成邊界移動，並提供可信 CSV 匯出。
5. **持續：規則精準度。** 以實際誤報資料修訂英文字邊界、短別名與 A+B 規則；公開清楚的命中依據與審核狀態，定期核對來源覆蓋空缺。
